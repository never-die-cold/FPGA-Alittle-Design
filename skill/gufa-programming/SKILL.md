# 古法编程（小步交付 + 逐步出题）

一句话规则：**AI 写代码可以，但不许一口气写完——每步 ≤100 行，出题过关再走下一步。**

名字取自"古法手作"：慢工细活，一小步一小步来。针对的痛点很具体——
大块 AI 代码一次倾倒，理解债集中爆发，最后在答辩/上机/debug 时一起还。

## 与 understand-gate 的分工

- **古法编程**：开发**过程中**的节流阀——把理解摊平到每一步，防止一次性倾倒
- **understand-gate**：commit **之前**的总闸——最终入库仍要逐段讲解 + 3 题
- 古法编程走得好，understand-gate 的补课轮次会显著减少（交付量小、理解已当场建立）

## 流程

### 第 0 步：拆步（写代码之前）

- 先给**步骤清单**：每步交付物、涉及文件、预估行数、验证方式（编译/仿真/波形）
- 单步粒度：一个模块 / 一个 always 块 / 一个函数 / 一个脚本功能点
- 预估超过 100 行（不含注释空行）→ 必须再拆
- 清单经用户确认后才开工；中途要加步/拆步，先说明再动
- 用 todo 清单维护步骤状态，用户随时能看到"第几步/共几步"

### 第 1 步：单步实现

- 只做当前这一步，不顺手改后面的东西
- 新增/修改 ≤100 行（默认阈值；用户可指定更小）
- 中间讨论可以照常展开，但**代码只给当前步**

### 第 2 步：本步自检

- 能跑就跑：编译/仿真/lint 的命令 + 原始结果，禁止只报"应该没问题"
- 本步无法独立验证（依赖后续步骤）→ 明确说明原因，不许含糊

### 第 3 步：讲解 + 出题（硬性卡点）

- **讲解**：本步设计意图（为什么这样写）、关键信号/变量为什么存在、
  与 `design_v0.md` 等设计文档的对应章节；术语首次出现给一句人话解释
- **出题**：2–3 道针对本步代码的"如果改成 XX 会怎样"，从零水平出发
- **等用户回答**，答完判定；不通过 → 针对缺口补讲 + 补 1 道新题再测，直到通过
- 禁止：替用户作答、放水降难度、没等回答就继续写

### 第 4 步：下一步

- 用户确认理解后才进入下一步
- 用户明确说"这步我懂，跳过出题"→ 可跳过该步题目（豁免要在收尾时留痕）

### 第 5 步：收尾

- 全部步骤完成：跑全量回归，按 `skill/understand-gate/SKILL.md` 走 commit 前流程
- 各步题目/答案/判定简要归档进 `report/llm_log/`（当日记录追加章节）

## 拆步示例

| 任务 | 推荐拆法 |
|:---|:---|
| 新 RTL 模块 | 接口 + 空实现 → 主逻辑 → 边界/复位分支 |
| 新 testbench | 骨架 + 激励 → 判据 + 自检打印 |
| 新脚本 | 参数解析 → 主流程 → 错误处理 |

## 失效条件（豁免）

- 纯文档 / `.gitignore` / `llm_log` / `data` 记录类改动
- 一行修复（typo、改常量）且用户认可
- 用户显式说"快速模式 / 别出题 / 一次写完"
- 探索性 spike（注定要扔的代码）——转正式实现时补走流程
- 用户已能独立复述该模块后，可按里程碑降频（如每步只留 1 题）
