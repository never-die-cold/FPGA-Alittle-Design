# 代码修正手册（bug-fix-playbook）

一句话规则：**修复前先分清"功能真坏了"还是"反馈坏了"；修复时先写出会 FAIL 的测试；修复后拿证据说话。**

## 适用场景

- 测试"全绿"，但功能在真机/联调中实际不可用（弱测试放过的真 bug）
- 用户报告"按了没反应 / 看起来不对"——先别改代码
- 只在真机、跨机、断联、重启等边界条件下出现的问题
- 时间戳/统计数字"对不上"的问题
- 需要在提交前证明"真的修好了"的任何修复

## 检查清单（按顺序）

### 1. 先分清"功能坏"还是"反馈坏"

- 查**落盘物证**（记录文件 / 日志 / 产物），不要先读代码
- 实例：用户报"按 c 没反应"，`records.jsonl` 里却有两条记录 → 功能是好的，坏的是"反馈只闪 33ms"（改常驻计数）

### 2. 弱测试巡检："跑通即通过"是假测试

- 断言必须检查**输出的可观测特征**（画面像素统计、落盘文件内容、报文字段），而不是"进程退出码 / 文件存在"
- 实例：`/v1/check` 误发 GET（404）导致叠框全失效，旧测试只验"跑通+出图"而全绿放过 → 补"绿色目标框像素 > 500"内容断言

### 3. 负例先行：修复前先写会 FAIL 的测试

- 顺序 = **复现 FAIL（留证）→ 修复 → PASS**。没有 FAIL 步骤的"修好了"不算证据
- 校验类修复用**矩阵式负例**：如"3 合法 / 12 非法"报文矩阵一次性覆盖
- 边界值成对写：合法边界（右下端点 = 图宽）与拒绝边界（退化 / 反向 / 越界）同时断言

### 4. 时间戳三问（比较任何两个时间戳之前）

- 谁盖的章？在什么时刻盖的？跨不跨机器 / 跨不跨阶段？
- 跨机比较一律改用**本地观测时基**（收到时刻），服务端时间戳只作诊断字段
- 实例："请求前取的钟"减"请求中盖的章" → 负年龄 → 每轮翻转（576 条异常日志）；修复后 1 条

### 5. 资格 / 来源标记放"采纳点"，不放"发动点"

- 对每个"标记 + 可能失败的后续动作"组合自问：动作失败后，这个标记还成立吗？
- 实例：手动轮标记写在"发请求"时会被失败路径污染（断联旧包冒充记录）→ 移到"报文被采纳"之后

### 6. 每个恢复路径问一句"如果恢复动作自己也失败呢"

- 重连 / 重试 / 重握手函数必须自带异常处理，失败时降级为"保持等待"而不是崩溃
- 实例：连续失败后自动重握手，服务仍不可用 → 异常外泄崩溃（已修）

### 7. 自愈条件显式化，别靠计数器间接推断

- 远端身份变化（session 更换）必须**显式比较并触发重建**；计数器会被"之后的成功请求"清零而悄悄失效
- 实例：服务重启后永久 WAITING（已修）

### 8. 反馈 = 持久状态，不是瞬时事件

- 成功提示要"常驻可再观察"（常驻计数），不是只存在一帧的闪烁
- 状态在任意时刻可查；事件只有当场可见

### 9. 事件按边沿记录

- 状态机的日志只记**迁移沿**（状态变化），防逐帧刷屏
- 实例：正常/断联全程 1 条 vs 修复前 576 条

### 10. 新症状先怀疑最近改动

- 排障优先级：最近的 diff → 关联模块 → 全链路；回归相关性优于随机猜测
- 实例：同日两问题（flap + 反馈）互相遮蔽——先修 flap 后，反馈问题立即暴露

## 与其他 skill 的分工

- 本手册管"**坏了怎么修**"；新功能怎么写见 `gufa-programming`；入库讲解门槛见 `understand-gate`

## 失效条件

- 需求本身有歧义——先澄清需求，这不是 bug
- 纯性能问题——走基准脚本方法论（见 `big-rewrite-playbook` 第 5 条）
- 第三方依赖缺陷且无替代——记录并规避，不做"修复"
