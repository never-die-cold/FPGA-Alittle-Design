## 2. 模型第一版方案（经用户两轮修订）

- 初版：从零定义接口 → 用户重读整理后的文档（PR #31/#32 合并态 + 通用 tb）后，改为**锚定既有 tb**，只补齐它缺的部分

- 关键决策（用户拍板）：
  1. 观测协议 = 观测块（DMEM 顶部保留区）+ `tohost=crcfinal`（现有 tb `+exp_tohost` 即可判 golden）
  2. 评分口径 = 移植层官方 `start/stop` 读计数器，`CoreMark/MHz = iterations × 10^6 / (t_end − t_start)`
  3. 仿真档 = 2K profile、`ITERATIONS=32`；`crcfinal` 用 PC 同源 golden（两路复核），三常数直接写死
  4. 计时计数器 = 主动提案 `0x8000_8000` + 同拍组合读，标注"待 RTL 线确认"

## 3. 失败现象与偏差（如实记录）

1. **官方 10 秒陷阱**（调研发现）：`core_main.c` 对 <10s 运行 `total_errors++`；仿真 32 迭代必然触发——朴素思路"程序没报错即 PASS"在仿真下必然误判 FAIL，契约改为"判据看 CRC、`errors_raw` 只作证据"
2. **三常数 vs crcfinal 的时机差异**（官方源码核实）：`crclist/crcmatrix/crcstate` 与迭代数无关可写死；`crcfinal` 迭代相关必须 golden
3. **接口缺口延续**（历史教训同类）：计时计数器地址在 `design_v0.md` 尚未冻结 → 契约为其设"提案 + 待确认"机制
4. **工具小坑**：PowerShell `Get-Content` 行数统计误报（99 vs 实际 127）→ 改用字节级 LF 统计
5. **流程偏差**：用户指出"写得太繁琐"→ 拍板**只减流程**（§6/§7 合并一步、免理解题、收尾从简），文档内容不缩水

## 6. 古法编程理解门槛记录（题面 / 用户答案 / 判定）

**第 1 步（范围与依赖）**

- Q1 契约权威为何唯一：答"以初始设计为准，都自称权威会冲突" → ✅（补正：接口最终解释权唯一，否则三方各引各版）
- Q2 计数器地址为何不能先随便选：答"两环境会混乱" → ✅（补正：同一 hex 双环境必须逐位一致）
- Q3 范围边界（计数器语义入、板上 10s 流程出）：答不上 → 补讲 → 补题（10s 是什么时间/跑满会怎样）→ 答"计时器测的、跑满与实际不符" → ⚠️ 补讲 → 终题（误用程序报错当判据会怎样）→ 答"误判失败、正确看 CRC" → ✅

**第 2 步（接口契约）**

- 观测块选址两理由 → 答"高位固定低位索引、避 tohost 重叠与数据栈" → ✅
- 计数器同步读的连锁反应 → 答"lw 写回拉长、要加停顿、CPI 不可比" → ✅
- 回绕减法 → 答 `0x20`=32 拍、模运算即真实周期 → ✅

**第 3 步（镜像与观测）**

- SHA-256 意义 → 答"可复现、同标准、改边界不可比" → ✅（补正：改算法后不再是 CoreMark）
- 跑飞防护三层 → 答"tb 给约束、提供提交点" → ⚠️ 补讲（看门狗/结束事件/封口三层）→ 补题（永不写 exit）→ 答"看门狗超时、判 FAIL" → ✅（现场字段由讲解补全）
- `tohost=crcfinal` 的理由 → 答"现有 tb 够用、信息量大于 1" → ✅

**第 4 步（判据）**：题目已给出（三常数 vs golden、公式量纲、golden 不一致处理）；用户随后选择流程减负、豁免出题——按 gufa 豁免条款留痕，不作判定。

**第 5/6 步**：合并收尾，按豁免不再出题。

## 7. 经验沉淀

- 触发条件：给"需要跨线共用"的基准/接口写契约；或官方基准移植前的判据设计。
- 排查步骤：
  1. 契约先锚定**既有实现与已冻结文档**，只补缺口，不从零发明接口；
  2. 未冻结的接口用"提案 + 待确认 + 收口标志"表达，不阻塞其他节；
  3. 官方基准的隐含规则（如 10s 有效性）要在契约里写成**显式禁令**，并把"判据"与"证据"字段分离；
  4. 金标准（golden）必须双路复核、禁止二选一。
- 适用范围：换基准（Embench）、换板卡、换工具链仍成立。 #skill候选
