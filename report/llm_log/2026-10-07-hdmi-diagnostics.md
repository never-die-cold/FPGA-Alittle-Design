### 第1题：R0 = bit0:1, bit3:1, bit4:0，HDMI 显示什么？

**显示彩色原图，和全关时一模一样——但前提是这组值经过 R11 提交并等到帧首生效。**

依据（design_v0.md:98 的 R0 位定义）：

- bit0 = `gauss_en`，bit3 = `sobel_en`：这两个开关**只作用于分析支路**（rgb2gray → gaussian → sobel 的灰度诊断口 `out_*`）。bit0+bit3 同开 = 先高斯平滑再做 Sobel 边缘，得到抗噪的边缘图。
- bit4 = `diagnostic_display_en`，默认 0 = **显示原图**。HDMI 的显示源由它选择：0 → 原图彩色直通；1 → 才把分析结果按原图位置换上屏。

关键机制是**双路径拓扑**（design_v0.md:24-27）：`display_*` 彩色原图是**恒延迟直通**线，分析开关“均不影响”（design_v0.md:81）；灰度诊断口“不驱动物理 HDMI”。所以 bit0/bit3 怎么开，HDMI OUT 的画面都不动。可以观察到变化的只有诊断口——灰度流变成了“平滑后边缘图”（可经 JTAG/ILA 看到）。

**为什么这样设计是对的**：显示延迟固定（4968 拍，与配置无关），分析链的开关、缩放、反压都不会让画面抖动或移位；这也正是验收口径“画面无变化 = 正确”（onboard 记录）的来源。

### 第2题：为什么分析流的单拍 VS/HS 不能直接驱动 HDMI，而要延迟完整 RGB/VS/HS/DE？

一句话：**单拍 VS/HS 是内部对齐标记，不是显示器认的同步波形；HDMI 必须由原始光栅驱动，分析结果只能“换像素、不换时序”。**

具体三层原因：

1. **两套信号语义不同**。内部像素流约定（design_v0.md §3.1）里，`vs` = 帧首**单拍**标记、`hs` = 行尾**单拍**标记——它们的作用是清 x/y 计数、做行帧对齐。而显示器（rgb2dvi/TMDS）需要的是**连续、极性和宽度稳定**的 VS/HS 完整波形，靠它锁相。设计文档明确写了分工：“完整原始同步波形用于 HDMI，分析支路的单拍 VS/HS 只作内部标记”（design_v0.md:21）。
2. **分析支路的时序是抖的**。高斯/Sobel 各带一行缓存延迟、首像素延迟 50 拍；scaler 吞吐 1 像素/2 拍、未就绪会挂起；cop_buf 快照受 `cop_ready` 整帧许可。拿这条支路的 VS/HS 当显示同步，同步会随处理延迟漂移——画面撕裂、滚动甚至失锁。
3. **所以要“整捆延迟”而不是“重新生成”**。`diagnostic_display` 把 `{frame_epoch, mode, VS, HS, DE, RGB}` 29 位打包，**整体**推进一个 4966 深的环形 FIFO（`raster_delay`，总延迟 3×H_TOTAL+18 = 4968 拍 ≈ 3 行 + 18 拍），输出时只把 DE 有效窗口内的 RGB 换成灰度（`video_rgb = q_mode ? gray : q_rgb`，diagnostic_display.v:47）。因为 VS/HS/DE/RGB 走同一个延迟线，它们**永远互相对齐**：显示器看到的是一条合法、恒延迟的 720p60 光栅，变的只是 DE 窗口里的像素内容。

为什么延迟取 3 行：gaussian 和 sobel 的行缓存各让输出行落后输入 1 行，加算术流水 ≈ 3 行——把原图也推迟同样多的光栅时间，第 N 行的边缘灰度恰好能在第 N 行的延迟光栅位置上被读出（“按原图位置读出”，design_v0.md:18），画面才不会上下错位。

### 第3题：帧中途直接改显示配置、不走 R11/R12，会出什么问题？

**画面会撕裂，证据会失效。** 假如寄存器写了立即生效（没有暂存-提交-确认这层）：

1. **一帧两种配置，画面撕裂**。R0–R10 各位在不同拍被采样，生效位置各不相同：Sobel 半帧开 → 上半帧原图、下半帧边缘图；OSD 检测框写到一半换坐标 → 一框两段、断在行中；ROI/框位置改了 → 旧框没画完新框已开始。
2. **行内花屏**。gaussian/sobel 的 3×3 窗口靠行缓存装配，行中途切配置，窗口里新旧参数混着算，边界若干行出假边缘；流水使能中途翻转还会打断 DE 像素流的连续性（少像素/多像素），显示段错位。
3. **同步失稳**。若改动涉及几何/时序类参数，帧中途改变光栅，显示器直接失锁（黑屏/滚动）。
4. **验收证据不可复现**。PS 不知道改动从哪一帧起生效——golden 对拍、`display_frame_id`/`cop_frame_id` 与配置的关联全部失去依据，M3 验收没法存证。

R11/R12 协议正是为消灭这四条（design_v0.md:118-121）：

- **R0–R10 只是暂存区**，写了不生效；
- **R11 写 1 整组提交**，config_bridge 在**下一个帧首（消隐期）整组原子应用**——“开关切换在帧边界生效（消隐期切，避免撕裂）”（design_v0.md:41）；
- **R12 递增回读已生效的配置编号**（注意：是配置编号，不是帧计数——这是之前 watch 工具踩过的坑），busy 期间重复提交回 SLVERR，无视频时 busy 常驻、须超时报错（`VisionRegs.commit()/wait_applied()`）。

所以任何已提交配置都从一条干净的 VS 边界开始，新旧配置永远不会出现在同一帧里。tb 层面已有等价覆盖：帧内改 R0 当前帧不变（tb_top 帧锁存验证）、“帧边界切换参数不撕裂”是 §4 的波形专项红线（design_v0.md:164）。

一点补充给第 1 题：如果这组 R0 值**只写暂存、没按 R11**，那么连分析支路都不变——暂存区的任何值都要等帧首整组应用才生效。三道题背后的同一条主线：**显示要稳（恒延迟原始光栅），配置要原子（帧首整组 + 编号确认）**——这就是 M2 显示链可验收的根基。
