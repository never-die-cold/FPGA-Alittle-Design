## Q1 park 判据换代：为何去掉 bit3、安全防线在哪 —— PASS

owner 答案要点：bit3 在 RTL 中即 `epoch != 0`（capture_status_axi.v:83），是历史锁存位，
启动瞬态发生后长期为 1，继续用会永久拒启健康链路。防线列举完整：lock 必须在位；
暖机批准及之后 pending(bit2) 必须清；批准后 epoch/overflow/lock_loss 相对基线零增量
（轮询间闪断也会留下累计证据）；正式捕获/复制期任何 DMA 错误即拒；运行态/槽位/描述符/
overlay 身份联合确认；复制前后确认停在槽 1 保护槽 0。判定：与实现一致且补齐了
RTL 级依据（agent 未引 capture_status_axi.v 原文，owner 补引）。

## Q3 瞬态吸收窗口：基线为何放批准点、边界何在 —— PASS（并补充边界）

owner 答案要点：启动前基线不含瞬态会把正常启动误判为新故障；刚写 RUN 时重定太早
（硬件恢复未完成）；批准点要求运行态正常+错误清零+槽位到 1+IRQ+pending 清，此时
只更新软件比较基线、不清硬件计数；暖机帧不直接交付。**owner 指出实现的真实边界**：
当前实现吸收批准前全部累计事件，未强制"只允许一次启动溢出"，暖机期自愈的真实故障
同样会被纳入基线；"恰好一次"是部分实验现象（亦记录过零瞬态启动）非代码保证。
兜底：有界等待、批准严格检查、批准后零容差、复制前后复查。该边界已回写契约
§10/16"已知边界"条目。判定：PASS，且优于 agent 原表述。

## Q4 EXE REQUEST_TIMEOUT 2→300s：为何是过渡、如何回收 —— PASS

owner 答案要点：300s 只改等待预算，未消除耗时来源（板上 locate+NumPy CNN 整轮
实测 94–122s）；2s 会把正常慢执行误判超时。代价：故障发现变慢，且公共 `http_json()`
使 status/config 请求共享 300s 预算；等待预算 ≠ 结果有效期 max_age。回收路径：
C03 硬件 CNN 接入后按**完整轮次**实测冷启动/稳态/最大目标数耗时再收紧检查请求；
status/config 恢复短超时；复验超时/断联/重连/旧结果撤框；是否回到 2 秒由整轮实测
决定，不能只看 CNN 算子变快。判定：PASS（"预算≠时效"与"整轮实测定回收"两点
优于 agent 原表述，已按此口径归档）。
