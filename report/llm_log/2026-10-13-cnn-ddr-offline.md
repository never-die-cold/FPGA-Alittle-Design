## 面向理解的讲解

- signed扩展重复符号位，才能保持负数数值；overflow表示数学结果超出INT32，result位模式无效。
- 流水线valid是“这一拍的数据属于真实计算”的标记。CE=0时数据和标记都暂停；abort清标记，旧数据即使仍在寄存器也不会被当新结果消费。
- 地址阶段先计算坐标与行/块，再形成最终word地址；减少跨寄存器的组合级数，代价是控制器周期增加。理论128MAC下界不是实际调度延迟。
- ReLU只改变负激活，requant按统一整数定义舍入/饱和；不能先截位或用算术右移替代负数半值舍入。
- DDR的IRQ、Halted和stream_seq各自只说明部分事实。必须确认真正的整帧、确定且不再复用的slot，再invalidate并复制，才能将独立图像交下游。
- 新CTRL/服务包装尚未实现；当前计算器ready/done不自动满足C03的模型校验、权限、sticky错误和原子快照规则。

```markdown
## 1. 负乘积补零扩展 / 溢出后饱和继续计算

**补零扩展的后果是"静默的、有方向的数值错误"，不是崩溃。** 举个例子：激活 −1、权重 +2，16 位有符号乘积是 −2（`0xFFFE`）；若把它补零扩到 32 位变成 `0x0000FFFE` = **+65534**，一笔负乘积就引入 +2¹⁶ 的正向偏置。这个错误在求和树的每一级都可能犯——`src/coprocessor/mac_array_pipeline.v:37,41,44,45` 每级加法都要多扩一位符号位（`{products[2*i][15], ...}` 这类写法），`src/coprocessor/int8_mac.v:14` 的 `{{17{product[15]}}, product}` 同理，任何一处漏掉就是按位宽平移一个负数。

危害为什么特别大：

- 8 路点积里最多 8 笔负乘积，累计偏置可达 **+524,288**，而 8 项点积真值上限只有 8×127×127 ≈ 129,032——**偏置比整个合法信号大 4 倍以上**。
- 偏置恒为正，不会触碰 INT32 边界，所以 `overflow` 标志根本不响；被抬起来的"负数"经 ReLU 变成合法正激活，logits/margin 仍是"看起来正常"的数 → **系统会以完全正常的姿态给出错分类**，这比报错恶劣得多。
- 错误方向系统化（负贡献越多越偏向正），等价于给网络叠加了一个非线性偏置，argmax 会稳定偏向某类。

这也解释了为什么这个设计把算术契约钉死在最小原语上：`tb_int8_mac` 穷举全部 65,035 组合法 INT8 组合（含大量负数），任何扩展写错在第一步就红，轮不到网络级去抓。

**溢出后饱和继续的后果是"把约束违规伪装成精度损失"，且不可逆。** 饱和是钳位、不是运算：一旦把越界的部分丢掉，后续再加再减都恢复不了它（结果还依赖累加顺序），参考模型做不到、也预测不了这个行为。本设计的回答是反向的——

- `int8_mac.v:14-16`：用 33 位宽算和，`overflow = total[32]^total[31]` 只在"结果不能精确表示为 INT32"时置起；**溢出 = 结果无效**，调用方必须拒绝，不做补救（文件头注释 "callers reject overflow, never saturate"）。
- 数组流水同款（`mac_array_pipeline.v:45,48`），控制器把它升级为任务级错误：置 `error`、记层号、**不发布 DONE**（`cnn_sequencer.v:111-112`）。溢出真正说明的是"上游契约被破坏"（权重范围、累加界预检失败），此时唯一正确的反应是大声失败，而不是继续算出一个貌似合理的分类。

饱和在这个设计里只出现在一个地方——requant 输出钳到 [-127,127]（`int8_requant.v:20-21`）。那个饱和是被定义、被 Python 参考逐位镜像的数值契约的一部分；而且 requant 内部刻意先做 32×32→64 位精确乘、再做舍入（`:16-19`），**不在任何中间环节丢值**。区分标准就一条：输出级饱和是规格；累加中途饱和是把规格违规悄悄吞掉。

## 2. CE 暂停时数据停住、valid 继续移动

先明确 valid 的定义：它是"**这一拍寄存器里的载荷属于真实计算**"的令牌，所以必须与载荷**同门、同拍**。`mac_array_pipeline.v:15-22` 正是这么写的——valid 移位寄存器和数据寄存器共享同一个 `ce` 门，`abort` 清 valid；注意第 3 行注释：**数据寄存器刻意不复位**（复位它们没有意义），valid 是唯一必须被好好管理的东西。

如果两者分离（valid 不受 `ce` 门，或按"固定等 N 拍"而不是看 valid），暂停期间令牌穿过各级而载荷停在原地，暂停结束后 `out_valid` 标的是**错误的一拍**，具体会误消费哪一类数据：

- **重复消费**：把已经算完/已经该写的上一拍再当新结果消费一次（同一输出元素写两遍，或与下一拍错位一格）；
- **静默丢失**：真正的某一拍永远等不到自己的 valid，输出不写——而特征 bank 在整个 busy 窗口不清零，旧值留在原地，下一层就对**旧激活**做卷积。错误不是丢一拍，而是空间上扩散；
- 被"误当有效"的既可能是上一个点积的残拍，也可能是 abort 中断任务的残留，或各级半新半旧时形成的瞬态组合。

这类错误的可怕之处在于它是时序相关的：只在内存争用、CE 暂停、HDMI 抢占这类事件发生时才出现——典型的偶发 heisenbug。所以只能靠结构保证（valid 随数据暂停），不能靠事后调试。

**复位/abort 为什么还要清 valid**：因为数据寄存器不复位，abort 的那一刻流水线里还"漂着"几拍旧数据；valid 不清，这些**孤儿拍**就会以合法标记继续流出：被算作新任务的输出、把上一任务的 logits 写进结果寄存器（`cnn_sequencer.v:141` 的结果捕获就是吃 `engine_write` 的最后一拍）、或在复位恢复后与新任务的头几拍混在一起产生**假 DONE**。清 valid 建立的"流水线中无在途令牌"不变量，是 `start`/`abort` 语义能成立的前提。而 abort 的来源不只是复位：watchdog 临近 `cycle_limit` 也会 abort（`cnn_sequencer.v:55,67,100-101`），被 watchdog 终止的任务更不能让残拍晚到、晚写。

顺带一提，`ce` 的"同门"要求不限于数据与 valid：读使能、写使能、地址全都带 `ce`（`cnn_sequencer.v:76-86`），否则暂停期地址会与数据错位，是同一类协议破坏。

## 3. DDR 完成中断后为什么还要三步

因为 **IRQ 只说了一件很有限的事**："帧计数条件发生了"（FrameCntEn=1、IRQFrameCount=1）。它没有说：

- **写通道已排空**——在途的写 beat/BRESP 可能还在互联里，最后一拍可能尚未落地；
- **通道已停**——自由运行配置下，IRQ 后下一帧立刻开始写；
- **帧落在我的槽里**——完成的是我配置的 slot 0 描述符，而不是别的；
- **源侧安静**——halt 后仍到来的 stream 是被"接受并丢弃"的，`stream_seq` 增长**不是** DDR 完成证据（交接文档原话）。

所以 `src/pynq_host/c01_capture.py` 的 `_protected()`（`:69-79`）做的是联合确认：SR 的 Halted+IRQ、CR 运行位为 0、无 DMA/CAP 错误位、park slot 恰为我方槽位、描述符寄存器（地址/HSIZE/STRIDE/VSIZE）未变、采集源身份/几何/错误事件未变。**只有这个合取**才能推出"完整一帧停在属于我们的、已不可能再被写的槽里"。只看 IRQ 就复制，要么抢跑最后几拍（帧尾缺或混入旧内容），要么已经被下一帧覆盖——得到上帧头+下帧尾的拼图，**它仍然像一张图**，最坑。

- **invalidate**（`:142`，复制之后是 `:144`）：DMA 从 S2MM 直接写物理内存，CPU 侧缓存里可能残留该区域的旧行（分配清零、以前读过）；不清缓存就复制出"缓存旧行 + DMA 新行"的混合帧——形状、dtype、字节数全对，肉眼还像图。同时它防止 CPU 脏行以后写回、盖掉 DMA 新数据。
- **复制独立副本**：DMA buffer 的内存所有权必须留在硬件侧（还要复用），把裸视图交给下游等于生命周期缠绕——下一帧覆盖它、或在 DMA 还在写时被析构器释放（这就是 `QUARANTINE` 强引用、未确认停机一律不释放、进程不许退出的原因，`:15,179-184`）。`copy=True` 加 `shares_memory` 检查（`:144,150-151`）产出的帧不可变、自包含，下游可以任意慢。复制前后各验一次保护状态（`:140,:146`），期间若保护被破坏，证据留痕、帧可拒绝。
- 具体到"复制时 DMA 仍环绕复用 slot"：拷贝会与写竞争，帧内容取决于时序——不可复现、不可验证，而 PNG 本身看不出任何异常。

一句话总结：这三步把"硬件说发生了什么"升级为"软件持有不可变、一致、所有权单一的一帧"——**停止确认 = 所有权交接，invalidate = 可见性，独立副本 = 不变性**，三者各堵一个漏洞，缺一不可。
```

## 直接回答：“等 IRQ 再 invalidate 就发布”不行

失败点有两个，互相独立：

**1. 脏缓存行的清写时机不受控——invalidate 救不了已经写进 DRAM 的覆盖。** CPU 预填不 flush，意味着Uncache行还躺在 L1/L2 里没有落盘；画框线程继续写，又添一批脏行。这些脏行**什么时刻被踢出缓存回写到 DRAM，是无法预知的**——被别的进程的访存替换、被中断处理触及、甚至被维护操作触发都可能。而同一块 DRAM 正在被 S2MM 逐行写覆盖。于是：

- 画框的脏行若在 DMA 写完**该区域之前** eviction，会被 DMA 数据顺带覆盖，无害；
- 若在 DMA 写完**之后** eviction，几行 CPU 数据就覆盖了画面同一区域——帧坏了；
- 事后 invalidate 只做“丢弃 CPU 侧陈旧行”这个单向动作，对**已经落进 DRAM 的错误覆盖无法恢复**。

所以“等 IRQ 后 invalidate”读到的是“DMA 数据、预填残留、画框残留的随机混合”。最恶劣的性质和上一轮说的相同：它几何上仍是一张完整的图——形状、dtype、字节数全对——**坏了你也不知道，运气好你也不知道为什么好**。这不是时序安排问题，是契约违反（DMA 持有期间出现了第三个写者），任何事后补救都补不回确定性。

**2. 发布语义本身不成立。** 这个 owner 的出厂契约就是 `c01_capture.py:1-5` 头注释：“只有独立副本、cache 失效后完整单帧、才能离开本 owner”。发布物永远是 invalidate→`copy=True`→`shares_memory` 断言后的独立帧（`:142-151`），**原 DMA 缓冲从不对外发布**——它要么复用、要么在停机确认后释放。且 IRQ 单独从来不是充分条件：上一轮已论证，发布要吃的合取是 `_protected()` 里那套（halted+IRQ、无 DMA/CAP 错误、park slot 恰为 slot0、描述符寄存器未变、源身份/几何/错误事件未变，`:69-79`，等待循环里每个轮询还重验源身份 `:133-138`），复制前后再各验一次（`:140,146`）。

## 本轮我会怎么处置（套现有机制，不发明新流程）

1. **先止血**：给画框线程立互斥——置标志，禁止新写。已经写出去的脏行收不回来（eviction 课本上就发生在“任意时刻”），但停止添新是恢复确定性的第一步；通过 `close()` 的 `may_write→CR.run=0→等 Halted` 停下 DMA（`:167-178`）。若身份核验发现代际变了，直接走未知属主分支，绝不越权 stop。

## 下一轮怎么安排

**缓存交接——定死一个顺序，一条规则：**

text
~~~scss
（预填若有）全部 CPU 写 → flush(clean) 整缓冲 → 启 DMA
~~~

`→ [busy 窗口 CPU 对缓冲零读零写] → IRQ + 联合确认`

`→ invalidate → 复制独立副本 → 再确认 → 发布副本`

- flush(clean) 的作用和 invalidate 对称：它是**把脏行提前落盘，让“来不及的 eviction”从根上不存在**。DMA 启动后再有碰缓冲的要求，一律回成“本来就不该 happen”，而不是事后打补丁；任何启动后的 CPU 触碰都作废本轮。
- 一个必须先验证的前置：当前驱动只用了 `buffer.invalidate()`（`:142`），**分配器是否有对称的 flush/clean 接口要上板核实**（evidence 里已记录 `coherent` 位，若缓冲本来就是 coherent 属性则软件同步不适用，分支按记录事实走，不靠猜）。若接口不存在，规则收敛成更简单的“DMA 缓冲零 CPU 写”：预填这种陈帧探测器整条放弃，改为源侧打标（上游时间码/HDMI 测试图）或用寄存器侧计数对账——不复用 infer，不自制 flush。

**画框位置——永远在独立副本上，不在原缓冲上：**

- 发布物是不可变副本，画框发生在发布链下游（显示/标注线程拿 `frame` 或它的二次深拷贝）；框的坐标这类元数据与帧一起传递，副本本身保持只读。
- 若多个下游消费且各自要叠注，各自再深拷一份，绝不共享写同一份。
- “想直接在原缓冲上画因为省一次拷贝”不成立：原缓冲此刻的全部价值是“存在且不被人碰”，省下的拷贝钱远不够赔一轮不可信帧。

**原缓冲的释放——沿用 single-use 所有权，不做跨轮复用：**

- 发布之后 `close()`，停机已确认，free 一次即止；停机不确认就隔离+进程保活，前面的规则原样生效。
- 下一轮是**新实例重新申请**：重新走严格几何/地址/重叠检查（`:96-106`）、重新取身份 token、重新 `_check_source`——而不是复用本轮已发布过的缓冲。连续运行/ping-pong 的槽位复用设计还是交接文档里挂账的未实现项，等板端单帧复测通过后再谈，不因这一次违例提前搭车。

## 补测判定：通过

用户正确给出：违规写入已破坏可证明的一致性，不能等IRQ再invalidate补救；本轮拒绝发布，先禁止并发CPU写入并安全停止DMA；未确认停机不free；下一轮在启动前完成CPU→device缓存交接，busy期间不触碰原缓冲，后处理使用独立副本/各消费者私有副本；single-use缓冲不跨轮复用。三道理解题及第三题补测通过，不再追加问题。

实现边界说明（不影响补测通过）：

1. `_protected()`检测硬件状态、描述符与源事件，不能自动发现任意CPU线程写缓冲。调用方必须禁止这种访问，并在已知违例时主动作废/记录/关闭；不能认为所有违例都已自动监测。
2. 用户提出只读发布物是合理的上层策略，但当前返回的独立NumPy副本默认可写，没有设置writeable=false；不可变策略需由上层明确实施，画框用私有副本。
3. 当前`capture()`的finally在函数返回前调用`close()`；原DMA缓冲在成功返回独立帧之前已释放，不必等下游发布以后才释放。
4. PYNQ v3.1已有`flush()/sync_to_device()`接口；是否coherent及板端具体缓存行为仍须依实际对象核对。coherent免除显式缓存维护，不免除CPU/DMA并发写的所有权约束。原文“Uncache行”按该段含义应为“尚未清写的脏缓存行”，不是uncached内存。
